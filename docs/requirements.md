# EcommerceMVP 需求说明

## 1. 产品目标

为电商企业内部提供一个可演示、可扩展、可追踪的 Agent 工作流 MVP。首版覆盖美工、销售和选品三个部门，验证项目分配、独立聊天上下文、受控工具调用、报表导入分析和商品图版本化编辑的完整产品骨架。

## 2. 用户与角色

- 管理员：创建演示员工、项目并分配项目成员。
- 美工员工：在被分配项目中上传商品原图并发起版本化编辑。
- 销售员工：导入销售报表并通过聊天和 Dashboard 查询受控指标。
- 选品员工：结合销售和库存数据获取确定性补货建议。

MVP 使用前端角色切换模拟员工身份。所有相关页面必须展示“演示角色切换，不代表真实身份认证”，后端仍完整保存部门、用户、项目、会话和消息归属。

## 3. 核心功能

### 3.1 公共工作区

- 总工作台展示三个部门入口。
- 管理员维护演示员工、项目和项目成员关系。
- 部门页只展示当前演示角色在该部门被分配的项目。
- 每个项目可建立多个相互独立的聊天，支持新建、重命名和历史查看。
- 每条数据至少可追溯 `department_id`、`user_id`、`project_id`、`conversation_id` 中适用的归属字段。

### 3.2 美工工作流

流程：原图上传 → 输入要求 → 千问图片编辑 Provider → 展示结果 → 继续编辑 → 保存版本 → 下载。

- 原图不可覆盖，文件存储仅保存路径与元数据到数据库。
- 图片版本记录父版本、提示词、模型、状态和创建时间。
- 消息可以引用原图与历史生成图。
- 失败请求保留并允许重试。
- M6 前采用 Mock Provider，不依赖真实 Key。

### 3.3 销售导入与分析

流程：CSV/XLSX 上传 → 字段识别/映射 → 校验 → 预览 → 人工确认 → 事务写入 → 报告。

- 文件不超过 10 MB，使用 SHA-256 检测重复文件。
- 校验必填字段、日期、数字、金额和业务重复记录。
- 保存导入批次、原始文件元数据、成功/失败行数和逐行错误。
- 任一事务性写入失败时回滚；错误行可导出。
- 所有查询通过受控 Tool；模型不得生成或执行任意 SQL。

### 3.4 选品分析

- 解析站点、平台、时间范围、品类或 SKU。
- 分别调用销售与库存查询 Tool。
- 后端计算趋势、环比、毛利、退款率、库存覆盖天数和库存压力。
- 后端确定性规则生成是否补货及建议数量。
- DeepSeek 只解释和组织结果，输出数据范围、指标、建议、风险与依据。
- 采购必须人工确认，系统不执行采购。

## 4. Agent 与上下文

- DeepSeek 文本模型调用是无状态的，应用持久化项目、会话、消息、附件、工具调用和 Agent Run。
- 请求上下文由部门系统提示词、项目摘要、当前结构化范围、近期消息、当前消息和最新工具结果组成。
- 追问可继承实体与数据范围；关键决策前必须重新调用 Tool 获取数据。
- 所有 Tool 使用 Pydantic 输入输出结构并记录参数、输出摘要、状态、耗时和错误。

## 5. 仿真数据

- 覆盖最近 18 个月、美国站、Amazon、健身器材。
- 商品包括龙门架、跑步机、哑铃、健身凳和拉力器。
- 固定随机种子并显式构造：龙门架增长但低库存、滞销积压、热销低毛利、季节性、退款异常，以及少量缺失/格式错误/重复导入行。

## 6. 非功能要求

- 默认 Mock 模式，无真实模型密钥也能演示。
- 本地和 Docker Compose 均可启动。
- API 输入、上传限制、工具参数和文件路径均需验证。
- SQLite、上传文件和生成文件不得进入 Git。
- 关键流程可追踪、可重试、可测试，固定数据可复现。

## 7. 首阶段范围（M0）

本阶段只交付工程底座：设计文档、目录与配置、FastAPI/SQLite 健康检查、React 首页、Docker Compose、最小测试和后续 Issues。不实现三个部门的完整业务流程或真实模型调用。
